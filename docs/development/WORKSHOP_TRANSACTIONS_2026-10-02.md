## Exact caller contract

`RealmWorkshopTransactions.supports(domain, type)` identifies the explicit reviewed set. Call `command(sim, domain, id, type, payload, {save(candidate)})` with the **current** simulation and the existing **synchronous** durable `worldSave`/character-store saver. The returned rule result controls success, sound and repaint. On refusal, report `error` or the rule's `text`; do not announce success or call the old save-after-mutation path again. Duplicate success performs neither save nor live adoption. A refused attempt does not reserve its receipt, so the same identity can retry after the storage problem clears. Existing canonical rules refuse altered terms under the same identity and refuse a second unique bow/fitting/reward under a new identity.

The approved names are sandbox `craft`; adventure `forge`, `arsenal-craft`, `socket`, `equip`, `trade`, `pursuit-fit`, `starter-claim`, `pursuit-claim`. Field-guide recipes already resolve to forge/bow craft/pursuit-fit; no `pursuit-craft` command exists. The two specifically inspected claims use their existing completed-objective/current-run prerequisites and once-only ledgers. This module does not create objectives or outcomes. Arbitrary story rewards are excluded.

The candidate starts from `Core.Simulation(sim.snapshot())`, then restores the actual local player, room, return position, paused and water context for the rules. The validated saved candidate retains the existing home checkpoint. The caller retains its existing deliberate modal-pausing policy; this adapter does not resume live time. It saves before adopting changed canonical adventure/sandbox/journal/nextEvent fields, retaining the live Simulation, state roots, player, path, clocks and actor/runtime objects. It rejects a reviewed command that starts changing movement, effects or unrelated canonical fields. Notifications produced only on the candidate are not copied into the live actor runtime; caller success feedback uses the actual returned text.

`cross-trade` is deliberately excluded: its `hostile(sim)` check reads live enemy modes. A fresh candidate would lose those modes and could permit trading during pursuit or windup. Combat, movement, healing, effects, class/soul choices, start/accept commands and other story grants keep their existing paths. Any later addition requires inspecting its real caller and runtime requirements.

Root adaptations: load this module after Core; expose fresh-context `workshopCommand(domain,id,type,payload)` using existing `worldSave`; route RPGUI's direct craft path and AdventureUI's supported commands through it; preserve the old runtime paths for unsupported controls. SandboxUI's supported `craft` path is another actual caller with the same ignored-save pattern; Root can route that exact type through the shared callback while preserving its refusal while paused. The test-only hook may expose the same callback for receipt/replay checks; it is not player UI.
